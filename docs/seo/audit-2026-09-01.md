**Is the build locally complete?** Yes, structurally — 22 unique routes, all reachable, no broken internal links, no missing assets. But it ships one real local-only defect (duplicate `/404.html` + `/404/index.html`, see §2) and one mobile-conversion-blocking bug (privacy note overlay, see §2) that must be fixed before this is "done."

**Is the Hostinger package technically ready?** Mostly. The ZIP has no wrapper folder, `index.html`/`.htaccess` at root, forward-slash paths, correct `index,follow` robots meta, and — notably — it already excludes the duplicate `/404/index.html` that exists locally. `.htaccess` is sound (HTTPS redirect, gzip, cache headers, security headers) but is missing a www→non-www canonicalization rule and HSTS.

**Is it ready to be publicly indexed?** Conditionally. The SEO fundamentals (unique titles/descriptions, canonicals, schema, sitemap, robots) are solid. The blocker is not indexability, it's that the mobile privacy-note bug (P0) will suppress WhatsApp conversions from the exact traffic segment (mobile, PY) this site is built for — fix that before spending any ad budget driving traffic to it.

**What prevents it from reaching maximum trust and organic performance?** (1) the mobile CTA-blocking overlay, (2) a real "dead zone" in the responsive header between 1024–1179px where both the phone number and the WhatsApp CTA button disappear, (3) heavy verbatim boilerplate repeated across 16 service pages (thin/duplicate-content risk), and (4) no verified proof elements (which is a correct, rule-compliant choice, not a bug — but it does cap trust until real project photos/testimonials can be added later).

## 2. Top findings

**P0-1 — Mobile privacy-note overlay hides the primary hero CTA buttons on first paint**
- Page/route: `/` (and confirmed on `/cotizar/`; the note markup and JS are identical sitewide, so this reproduces on every one of the 22 pages)
- Viewport: 360px and 390px (confirmed both)
- Evidence: `.privacy-note` computes to `position: fixed; z-index: 100` with a bounding rect of `{top:488, bottom:642, left:16, right:344}` at 360px — this is the *exact same screen region* as `.hero-actions` (`{top:503, bottom:553, left:31, right:329}`), i.e. the "Pedí tu presupuesto" (WhatsApp) and "Llamanos" buttons are physically behind the privacy note. On `/cotizar/` the same overlay clips the last line of the lead paragraph. It only disappears after the user taps "Entendido," and reappears every new browser session (`sessionStorage`-gated, not a permanent dismissal), so repeat visitors within a fresh tab hit it again.
- Why it matters: mobile is the dominant channel for a WhatsApp-first PY business, and this literally hides the two buttons the entire site exists to get people to tap, on the very first screen they see.
- Recommendation: reposition `.privacy-note` to a non-overlapping location on small viewports (e.g. anchor to the very bottom of the viewport below the sticky WhatsApp/Llamar bar, or make it a slim dismissible top banner instead of a mid-page card), and consider switching to `localStorage` so it doesn't reappear every session.
- Effort: small

**P0-2 — Responsive header "dead zone" from 1024px–1179px: no phone number, no header CTA, no bottom bar**
- Page/route: sitewide (header/footer are shared across all pages)
- Viewport: 1024px (one of the five viewports explicitly required for this audit)
- Evidence: `assets/css/site.css` — `.mobile-bar { display: none; }` fires at `@media (min-width: 1024px)` (line 287), while `.desktop-nav { display: flex }`, `.header-phone { display: inline-flex }`, and `.header-cta { display: inline-flex }` don't fire until `@media (min-width: 1180px)` (lines 324-328). Confirmed live at 1024×900: `menuToggle: grid, headerPhone: none, headerCta: none, desktopNav: none, mobileBar: none` — only the hamburger icon and the floating WhatsApp FAB are visible.
- Why it matters: 1024px covers real devices (iPad landscape at 1024×768, many small/older laptops, browser windows not maximized). In that range visitors lose both fixed conversion paths (header CTA/phone and the sticky mobile bar) and are left with only a hamburger menu and a small FAB — a real regression sitting between two otherwise-fine breakpoints.
- Recommendation: move the `.mobile-bar { display:none }` cutoff to `1180px` to match the desktop-nav breakpoint, so there's no width where both are hidden.
- Effort: small

**P0-3 — Duplicate `/404.html` and `/404/index.html` in the local build (with mismatched canonical)**
- Page/route: `404.html`, `404/index.html` (local folder only — the ZIP is clean, see §11)
- Evidence: `diff` shows the two files are byte-identical. Both declare `<link rel="canonical" href="https://carpinteria.com.py/404/">` and `og:url` = the same. `.htaccess` (`ErrorDocument 404 /404.html`) treats the flat file as the real error document, making `/404/index.html` an orphaned, unlinked, but directly-browsable duplicate (HTTP 200, not 404).
- Why it matters: it's dead weight in the local repo that could confuse future edits (someone edits the wrong copy), and if it were ever left in a real deploy it would create a live duplicate URL. `noindex,nofollow` prevents it from being indexed, so it is not itself a launch-blocking SEO issue — but it is exactly the kind of stray file a "locally complete" build shouldn't ship.
- Recommendation: delete `404/index.html` from the local source folder (keep only root `404.html`, matching what the ZIP generator already correctly does).
- Effort: small

**P1-1 — Sitewide verbatim boilerplate across all 16 leaf service pages**
- Page/route: cocinas, placares, muebles-tv, escritorios, vanitorys, comercial, puertas, portones, pergolas, decks, machimbre, ventanas, blindex, cerramientos, escaleras, restauracion
- Evidence: the process-band ("Cómo funciona la consulta" / 01-04 steps), the decision-grid intro sentence, the FAQ-section intro sentence ("No publicamos precios, plazos o garantías genéricas..."), and the quote-band CTA paragraph are word-for-word identical across all 16 pages.
- Why it matters: roughly 40% of each service page's visible body copy is templated and unchanged from page to page — a duplicate-content signal for Google and a "robotic" feel for anyone who browses more than one service page in the same session (which is a normal path for a visitor comparing cocinas vs. placares, for example).
- Recommendation: keep the structure but vary the wording per page (even light synonym/example swaps referencing the specific service) for these four blocks.
- Effort: medium

**P1-2 — `/muebles-tv/` FAQ uses the word "mampostería" (masonry)**
- Page/route: `/muebles-tv/`
- Evidence: FAQ answer states it's important to indicate "si la pared es de mampostería, placa u otro sistema" (whether the wall is masonry, drywall, or another system).
- Why it matters: the business rules explicitly exclude masonry — that's obra.com.py's territory. The intent here is legitimate (identifying wall type before mounting a floating TV rack), but naming "mampostería" specifically blurs the scope boundary the rest of the site is careful to maintain (e.g. `/machimbre/`'s FAQ explicitly excludes roofing/structural work).
- Recommendation: reword to "tipo de pared" (wall type) without naming masonry specifically.
- Effort: small

**P1-3 — Video-tab controls (`role="tablist"`) have no keyboard arrow navigation**
- Page/route: `/` hero video selector
- Evidence: `site.js` only attaches `click` listeners to the four `.video-tabs button` elements (all 4 remain in normal Tab order; no `keydown` handler for ArrowLeft/ArrowRight/Home/End, no roving `tabindex`).
- Why it matters: `role="tab"`/`role="tablist"` signals to assistive tech that arrow-key navigation should work per the WAI-ARIA APG pattern; it doesn't here. Not a hard blocker (the buttons are still individually focusable/operable), but it's a real gap against the pattern it claims to implement.
- Recommendation: add arrow-key handling and roving `tabindex`, or drop the `tablist`/`tab` roles if staying click/Tab-only.
- Effort: small

**P1-4 — Hero video: all 4 external CloudFront videos load within ~2 seconds regardless of interaction**
- Page/route: `/` hero
- Evidence: `site.js` schedules `loadDeferredVideos()` via `requestIdleCallback`/`setTimeout` at a 1.2–2.2s timeout, and independently auto-advances the visible tab every 7 seconds. Combined, all four full MP4s (hosted on an external CloudFront distribution, not a first-party asset) are fetched within the first several seconds of any page load, whether or not the visitor ever touches the tabs.
- Why it matters: this is real, uncontrolled mobile-data cost on Paraguayan connections for four video files whose sizes aren't even visible in the HTML (external CDN), plus a single point of failure — if that CloudFront distribution/account is ever taken down, the whole hero breaks with no local fallback or poster image.
- Recommendation: don't preload/auto-advance through videos the user hasn't reached yet — load each video only when its tab becomes active (on click or on actual rotation to it), and add a `poster` attribute per video.
- Effort: medium

**P1-5 — `.hero-eyebrow` text likely fails WCAG AA contrast**
- Page/route: sitewide (every page's hero eyebrow label, e.g. "MADERA · MUEBLES A MEDIDA · ALUMINIO Y BLINDEX")
- Evidence: CSS computes `color: #5d5146` on a `#f2b15c` background — an estimated ~2.7:1 contrast ratio, well under the 4.5:1 AA requirement for normal-size text (the eyebrow is small/uppercase, not exempt as "large text").
- Why it matters: fails accessibility for low-vision users on a label that appears at the top of every single page.
- Recommendation: darken the eyebrow color or add a scrim; verify visually with a contrast checker after the change.
- Effort: small

**P1-6 — No www→non-www canonicalization in `.htaccess`**
- Page/route: infrastructure (applies to both local `.htaccess` and the ZIP's identical copy)
- Evidence: the HTTPS-redirect block only checks `%{HTTPS}`/`X-Forwarded-Proto`; there is no `RewriteCond %{HTTP_HOST} ^www\.` rule.
- Why it matters: if DNS/hosting resolves both `www.carpinteria.com.py` and `carpinteria.com.py`, both would serve identical content with no forced canonical host — a duplicate-content risk despite the correct per-page `<link rel="canonical">` tags (canonical tags help but a host-level 301 is the standard belt-and-suspenders fix).
- Recommendation: add a www→non-www 301 rule matching the sitemap's non-www canonical URLs.
- Effort: small

**P1-7 — Quote form has no accessible error state beyond native HTML5 validation**
- Page/route: `/cotizar/`
- Evidence: `#quote-form`'s submit handler calls `event.preventDefault()` and builds the WhatsApp link; the `required` attributes on `proyecto`/`zona` trigger native browser validation, but there is no `aria-invalid`, `aria-live` region, or custom error messaging anywhere in the form.
- Why it matters: fine for most users (native browser validation UI does appear), but screen-reader users and any edge case where native validation doesn't fire get no error feedback.
- Recommendation: add an `aria-live="polite"` status region for a friendly Spanish error message on invalid submit.
- Effort: small

**P2-1 — FAQ questions are not exposed as headings**
- Page/route: every page with a FAQ block (home + 18 service pages)
- Evidence: FAQ items are `<details><summary>` with no `<h3>` wrapping the question text; screen-reader users navigating by heading list will not see FAQ questions at all.
- Recommendation: wrap the `<summary>` text in a heading element, or add `role="heading" aria-level="3"` to it.
- Effort: small

**P2-2 — 5 of 22 page `<title>` tags drop the "| Carpinteria.com.py" brand suffix**
- Page/route: `/vanitorys/`, `/comercial/`, `/machimbre/`, `/cerramientos/`, `/restauracion/`
- Evidence: e.g. `/vanitorys/`'s title is "Vanitorys y muebles de baño en Asunción" (39 chars, no suffix) while `/ventanas/`'s is "Ventanas de aluminio en Asunción | Carpinteria.com.py" (53 chars, with suffix).
- Why it matters: minor brand-consistency and SEO-snippet inconsistency across otherwise-templated pages.
- Recommendation: add the brand suffix to the 5 outliers (keep an eye on the ~60-char SERP display limit when doing so).
- Effort: small

Full P2/P3 detail is in §8–10; the ten above are the priority-ordered top findings.

## 3. What is already strong

- **Business-constraint discipline is excellent.** Across all 24 pages: zero fabricated reviews, prices, years-in-business, guarantees, RUC, address, certifications, hours, payment methods, or team names. The site actively *discloses* these omissions ("No publicamos precios, plazos o garantías genéricas") rather than hiding the gap — a genuinely rare level of compliance discipline.
- **Voseo is 100% consistent** across every page — no "tú" leakage, no "Escríbanos" found anywhere.
- **Image/video honesty is explicit and repeated**: home FAQ, `/trabajos/`, and per-image captions all state the visuals are illustrative references, not completed jobs.
- **Phone/WhatsApp number consistency is perfect** — `+595 995 628862` / `595995628862` matches exactly across every visible link, `tel:` link, `wa.me` link, and every JSON-LD `telephone` field, on all 24 pages.
- **Schema hygiene is strong**: every `HomeAndConstructionBusiness` block shares one `@id`, every `FAQPage` schema's questions match the visible FAQ text 1:1, `areaServed` is consistent everywhere, and a full-site search for `priceRange`/`aggregateRating`/`review`/`openingHours`/`address` returned zero matches — no forbidden schema properties anywhere.
- **Internal linking has zero broken links and zero orphan pages** — all 21 real routes are reachable and every linked path resolves to a real file.
- **`prefers-reduced-motion` is implemented correctly** in both CSS and JS (reveal animations and hero video autoplay/rotation both respect it, including live toggling mid-session).
- **JS is lightweight and clean** — no un-throttled scroll listeners, `IntersectionObserver` used correctly for reveal animations, event listeners properly delegated and cleaned up.
- **Local vs. production indexation split is implemented correctly and consistently** — every local page is `noindex,nofollow`, every ZIP page is `index,follow,max-image-preview:large,...`, with no mixed/inconsistent pages in either copy.
- **The double-frame hero and right-side desktop video panel** render as intended at 1440px and read as premium/intentional — this should be preserved through any fixes.
- **Scope discipline in copy** is strong beyond the one "mampostería" slip — `/machimbre/` and `/portones/` both go out of their way to explicitly fence off adjacent non-carpentry work (roofing/structures, gate automation) rather than blur into it.

## 5. Responsive and visual report

**360px / 390px (mobile):**
- No horizontal overflow detected on the homepage (`document.documentElement.scrollWidth === window.innerWidth` at both widths) — the base mobile layout itself is solid.
- **Confirmed defect**: the privacy-note card renders as a `position:fixed` overlay directly on top of the hero's WhatsApp/Llamanos buttons on first load (see P0-1). Reproduced identically at 360px and 390px, and on a second page (`/cotizar/`, where it clips body copy instead of buttons).
- Sticky bottom WhatsApp/Llamar bar and floating WhatsApp FAB both render correctly and don't visually collide with each other at this width.
- Touch targets: header hamburger (48×48), bottom-bar buttons (52px min-height), FAQ summaries (64px min-height) all pass the 48×48 minimum. The four video-tab number buttons are exactly 48×48 but packed with only a 4px gap — technically compliant, tight in practice (P2).
- Mobile menu (`<details>`-based submenus) opens/closes correctly and the hamburger's `aria-expanded`/`aria-label` toggle in sync with actual state.

**768px (tablet):**
- No horizontal overflow (`scrollWidth 760` vs `innerWidth 768`).
- Header still shows only the hamburger (desktop nav not yet active) — appropriate for this width.
- Both the floating WhatsApp FAB and the sticky bottom WhatsApp/Llamar bar are visible simultaneously here — a minor redundancy, not a defect, but worth a design glance since two persistent WhatsApp affordances stack at this width.
- The privacy-note overlay shifts position but still visually overlaps the video-tab number buttons (02/03/04 partially obscured) — lower severity than the mobile case since it's not blocking the primary CTA, but still an overlap worth tightening (P2).

**1024px:**
- No horizontal overflow (`scrollWidth 1016` vs `innerWidth 1024`).
- **Confirmed defect (P0-2)**: this is the "dead zone" — header phone, header CTA, and the sticky bottom bar are all `display:none` simultaneously; only the hamburger and the WhatsApp FAB remain. This is a real, live problem for anyone landing at exactly this common width.

**1440px (desktop):**
- No overflow; the double-frame editorial hero and right-side video panel render as clearly premium and intentional — this is the site's strongest visual moment and should be protected through any other fixes.
- The privacy note repositions to a bottom-right floating card at this width and no longer blocks any CTA, but it does visually sit over part of the video caption text ("Diseño a...") — low severity (P3), it's in a corner and dismissible.

**General:** keyboard focus states were not exhaustively tested pixel-by-pixel across all interactive elements, but the underlying JS confirms `aria-expanded`/`aria-selected` states are correctly kept in sync for the hamburger, mega-menus, and video tabs — the remaining gap is the missing arrow-key pattern on the video tabs (P1-3), not broken focus management.

## 6. CRO report

**Value proposition clarity:** Strong. "Carpintería a medida en Paraguay" plus an immediate service list (cocinas, placares, muebles, puertas, pérgolas, decks, aluminio, blindex) and geographic scope (Asunción y Gran Asunción) in the first two sentences — a visitor knows what this is and whether it applies to them within seconds.

**Entry-point clarity:** Good. The homepage service bento and the "Empezá por tu proyecto" rail both route by service before asking for any commitment, and the nav's three mega-menu groups mirror the same categorization — a visitor rarely has to guess which page to land on.

**CTA hierarchy and wording:** Correct pattern (WhatsApp primary in green, phone secondary in outline) repeated consistently sitewide — hero, mid-page quote-band, sticky footer, floating FAB. Wording is voseo-correct and action-oriented ("Pedí tu presupuesto," "Cotizá por WhatsApp," "Llamanos"). The one real problem is not the CTA design, it's that **the CTA is physically unreachable on first mobile paint** (P0-1) — this is the single highest-leverage fix on the whole site, since it undermines an otherwise well-built conversion funnel at the very top of it.

**WhatsApp-first conversion:** Correctly implemented. Every WhatsApp link carries a pre-filled, contextual message (varies per page/service where relevant), and the `/cotizar/` quote builder assembles a structured message (tipo de proyecto, zona, detalle) before opening WhatsApp — genuinely reduces friction versus a generic "contact us" link.

**Friction points:**
1. The privacy-overlay bug (P0-1) is the largest friction point on the site by a wide margin.
2. The 1024–1179px dead zone (P0-2) removes the fixed conversion affordances for a real slice of desktop/tablet traffic.
3. The quote form's only feedback on an invalid submission is the browser's native validation bubble — fine, but there's no branded/friendly fallback message (P1-7).

**Trust without fabricated proof:** The site handles the "no reviews / no completed-project claims" constraint honestly and repeatedly discloses that images are illustrative — this is the right call given the rules, and it reads as transparent rather than evasive. The homepage FAQ ("¿Quién realiza el trabajo?") answer is accurate but reads slightly like a lead-aggregator disclaimer ("recibe y organiza consultas por rubro") rather than warm small-business copy — worth a tone pass, not a rule violation.

**Honest alternatives to fake social proof** (since reviews/completed-project claims are off-limits): consider a simple "cómo trabajamos" process visual (already present), a short "por qué mandar fotos y medidas ayuda" explainer (already present in the 4-step process band), and — once real, verified jobs exist — a dedicated, clearly-labeled "trabajos verificados" section added later, kept separate from the current illustrative gallery.

**Reference gallery (`/trabajos/`):** Helps rather than hurts trust, specifically because of its explicit disclosure ("Cada visual está rotulado como ilustrativo. No contiene clientes, ubicaciones ni trabajos atribuidos a Carpinteria.com.py.") — this is the correct way to use AI-generated imagery without misleading visitors.

**Homepage content after the hero:** Sufficient — services bento, 4-step process, materials index, illustrative visual grid, coverage section, FAQ, and a final quote-band CTA. No thin-homepage concern.

**Final CTA per page:** Present and consistent on every page checked (quote-band + sticky bar + FAB).

**Mobile vs. desktop conversion:** Structurally mobile should convert best for this audience (WhatsApp-first, PY mobile-majority market) — but right now the P0-1 bug actively suppresses that advantage on first load. Once fixed, mobile should out-convert desktop given the CTA design; today, desktop (which doesn't hit the overlay bug except briefly at ≥1024 in a different way) is likely converting relatively better than it should, simply because mobile is broken.

## 9. Performance report

All numbers below are **measured** from the local files (byte sizes, declared attributes, code inspection) — no Lighthouse run was performed (not available in this environment), so no Lighthouse scores are reported or estimated.

**Payload (measured, local files):**
| Asset | Size |
|---|---|
| `assets/css/site.css` | 28.7 KB (unminified) |
| `assets/js/site.js` | 6.8 KB |
| `aluminio-ilustrativo.webp` | 137 KB |
| `cocina-ilustrativa.webp` | 69 KB |
| `comercial-ilustrativo.webp` | 76 KB |
| `pergola-ilustrativa.webp` | 167 KB (largest) |
| `placard-ilustrativo.webp` | 75 KB |
| `puertas-ilustrativa.webp` | 145 KB |
| Home page HTML | 28.2 KB (local) / 28.2 KB (ZIP) |

Total static (non-video) payload for a typical page load is well within reasonable bounds for a WebP-based site. **The real weight risk is the hero videos, not the images or code.**

**Images:** already WebP (good format choice); all carry explicit `width`/`height` (prevents layout shift); below-the-fold images correctly use `loading="lazy"`, above-the-fold hero images correctly omit it (eager by default, appropriate). **Gap:** no `srcset`/`sizes` anywhere — every viewport, from a 360px phone to a 1440px monitor, downloads the same full 1536×1024 WebP. This is the single biggest easy performance win available (P2).

**Hero video (biggest performance risk, P1-4):** 4 external CloudFront-hosted MP4s; only the first uses `preload="metadata"` initially, but the combination of a 1.2–2.2s idle-triggered preload of the other 3 plus a 7-second auto-rotate means **all four full video files download within seconds of page load on any connection**, whether the visitor interacts or not. On Paraguayan mobile networks this is a meaningful, avoidable data cost, and there's no `poster` frame and no first-party fallback if the external CDN has an outage.

**Fonts:** Google Fonts (`Archivo` 3 weights + `Inter` 5 weights = 8 weights total), `display=swap` is used (avoids invisible text), `preconnect` is set for both font domains — but no `<link rel="preload" as="font">` for the actual font files, so there's still a CSS-fetch round-trip before font discovery (P2). 8 weights is more than a site like this typically needs (P3, trim to 3-4).

**Render path:** CSS and Google Fonts `<link>`s are render-blocking (unavoidable without inlining/self-hosting), but `site.js` is correctly `defer`red and placed at the end of `<body>` — no unnecessary render-blocking JS found.

**Main-thread/INP risk:** low. No un-throttled scroll listeners; `.reveal` animations use `IntersectionObserver` (the performant pattern); menu/video-tab logic is small delegated listeners. The JS itself is not a performance concern — the video-loading *strategy* is.

**Mobile-network verdict:** the calm video cycling **does** waste bandwidth on mobile, specifically because of the interaction between the idle-preload timer and the 7-second auto-rotate (P1-4) — this is worth fixing before driving paid traffic, independent of anything else in this report.
